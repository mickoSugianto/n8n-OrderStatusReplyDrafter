02 · HOW IT WORKS

Six stages, plus recovery and error sections.

One workflow canvas with 8 sections: Recovery, Stage 1–6, Error. An order question becomes a verified Gmail draft, and nothing leaves without a human.

  1. STAGE 1

    Receive inquiry

    Reads the labelled Gmail message and claims it atomically in PostgreSQL so overlapping runs cannot handle it twice.

    Atomic claim
  2. STAGE 2

    Classify & extract

    Cleans the email, validates the sender and extracts the order number and intent as strict JSON.

    AI extracts
  3. STAGE 3

    Lookup order

    An exact, rule-based lookup checks the order number and that the sender matches the customer.

    Rules decide
  4. STAGE 4

    Prepare reply

    Fixed templates for missing or unknown numbers; otherwise AI writes from verified facts, then checks run.

    Verified facts
  5. STAGE 5

    Save Gmail draft

    Records draft intent, creates the draft in the original thread and reads it back to confirm.

    Write + verify
  6. STAGE 6

    Triage & you decide

    Labels the email (triaged or needs-review) and completes the ledger. You read and click send.

    You decide
  1. RECOVERY SECTION

    Bounded automatic and manual recovery

    Every 5 minutes a sweeper retries stuck runs once, only on steps that are safe to repeat. Uncertain draft writes are checked against Gmail first or held for a person to inspect.

    Retries are bounded
  2. ERROR SECTION

    Unfinished work stays visible

    Failures keep their ledger state instead of disappearing. A separate Slack alert workflow fires only on terminal, quarantined or pre-claim failures; the first transient blip exits quietly.

    Nothing dropped silently

03 · SAFETY & PATTERNS

Patterns that make it safe (and where else they apply).

Every reply passes deterministic checks before it is drafted. The same reliability patterns transfer directly to CRM, lead-routing and webhook-driven pipelines.

Drafts only, human review gate

Proven here

No node in the workflow sends customer emails. Strict JSON extraction, fixed templates for gaps, and a draft-only review step.

Where else it applies

Lead classification or scoring with a Slack or CRM approval handoff before any external write.

Atomic PostgreSQL claim

Proven here

ON CONFLICT DO NOTHING RETURNING on (mailbox, source_message_id) lets PostgreSQL decide ownership so retries and overlapping polls never draft twice.

Where else it applies

Preventing duplicate CRM records, double enrichment spend or duplicate invoice triggers on webhook retries.

Deterministic lookup & validation gate

Proven here

A separate GetOrder workflow does an exact match and checks that the sender matches the order’s customer email before any facts reach a prompt.

Where else it applies

Malformed, unverified or unauthorised payloads fail closed before touching downstream APIs or AI calls.

People handle exceptions

Refunds, multiple orders, conflicting info, prompt overrides and sender mismatches skip drafting and go straight to manual review with a needs-review label.

What the AI sees

Only the customer’s cleaned question and, for a verified match, that single order’s details are sent to Groq (with OpenRouter as fallback). Missing or unknown numbers use fixed templates with zero model drafting calls.

Alerts only when it matters

A separate stateless workflow posts to Slack for terminal, quarantined or pre-claim failures. The first transient blip exits quietly and is left to the 5-minute recovery sweeper.

Deep dive: durable phase ledger, bounded recovery & uncertain-write verification

Bounded automatic recovery

A 5-minute sweeper retries crashed runs once, only on steps that are safe to repeat because nothing has been written to Gmail yet. A 5-minute cooldown and a 1-minute settle window stop it racing a live run.

Uncertain writes are checked, not guessed

If a draft write may have happened, recovery reads the thread and drafts first. It adopts one verified draft, recreates once only when zero drafts and zero later messages are verified, or quarantines the request for manual inspection.

What it doesn’t do

  • Synthetic test data. Built and tested on synthetic orders and two controlled accounts, not live customer traffic.
  • Plain-text English, one order per email. No attachments or multi-order requests.
  • A consistency check, not authentication. Sender matching does not prove who the customer is.
  • A person reads every draft. It does not replace human review before sending.
  • Recovery is bounded, with no dashboard. One automatic retry on safe steps; anything uncertain waits for a person to name the draft they inspected.

These are transferable patterns. Order Status Reply Drafter is the only workflow built, tested and published here; the “where else it applies” notes describe where the patterns transfer, not other shipped products.

Key design decisions

  • Deterministic lookup, LLM limited to extraction and drafting. Exact matching and sender checks run in code before any order facts reach a prompt.
  • Atomic PostgreSQL claim per mailbox and message. A composite key stops concurrent polls from drafting twice.
  • Checkpoints, read-back and bounded recovery. Draft intent is saved before Gmail is called and read back to verify it. After an uncertain write, a draft is recreated only when zero drafts are verified; otherwise it is quarantined.
  • Human review gate on every reply. Refunds, prompt overrides, multi-order emails and sender mismatches go to manual review.
